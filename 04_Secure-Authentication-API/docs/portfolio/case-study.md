# Case Study — Secure Authentication API

**Author**: Mahesh Kumar | **Date**: 2026-09-20

## Problem

Authentication is one of the most commonly implemented, most commonly under-specified pieces
of a web application. Most tutorials show "login returns a JWT" and stop there — leaving three
questions unanswered that matter in practice: what happens if a refresh token is stolen and
replayed; can a user grant themselves elevated privileges at signup; and where should the
long-lived credential actually live in the browser, given that `localStorage` is readable by
any injected script.

## Approach

A FastAPI backend implementing registration, login (OAuth2 Password Flow), JWT access tokens,
rotating/revocable refresh tokens, and server-side-only RBAC, paired with a React frontend.
Rather than defaulting to the most common tutorial pattern (both tokens in the JSON response,
client stores both), the token-transport strategy was decided deliberately and documented
(`adr/0002-token-transport-and-refresh-rotation.md`) before implementation began: access token
in the response body (keeps Swagger/curl/Postman testing simple), refresh token only as an
`HttpOnly`/`Secure`/`SameSite=Strict` cookie (removes it from JavaScript's reach entirely).

## Architecture

React SPA → FastAPI (`api/` → `services/` → `repositories/`) → PostgreSQL, one-directional
dependency flow. Full diagrams: `docs/HLD.md`.

## Key Engineering Decisions

| Decision | Alternative Considered | Why This Choice |
|---|---|---|
| Split token transport (body + HttpOnly cookie) | Both tokens in JSON body; both as cookies | Balances XSS protection for the high-value refresh token against keeping the access token trivially testable — see ADR-0002 |
| Refresh rotation with reuse-rejection | Stateless refresh with no revocation | A stolen-and-replayed refresh token needed to be rejectable, not just eventually expiring |
| PyJWT over python-jose | python-jose (older FastAPI-tutorial default) | Smaller, more actively maintained surface for the HS256-only need — see ADR-0001 |
| RBAC re-verified server-side per request | Trust the JWT's role claim | A demoted/deactivated user's access needed to change without waiting for token expiry |
| `uv`-managed `pyproject.toml`/lockfile over `requirements.txt` | Range-pinned `requirements.txt` | Exact reproducible installs; `uv sync`'s strict reconciliation caught a real dependency omission during the migration |

## Challenges & Trade-offs

**A real, found-in-production-style bug**: `passlib` 1.7.4 (unmaintained since ~2020) breaks
against `bcrypt` ≥4.1's stricter 72-byte enforcement — a genuine version-compatibility failure,
not a hypothetical, caught within seconds of writing the first password-hashing test because
the test ran immediately after the code, not at the end of a batch. Resolved by pinning
`bcrypt<4.1` (task.md required passlib specifically, so it wasn't simply dropped).

**Process discipline vs. speed**: the architecture phase (HLD, ADRs) was initially skipped in
favor of moving straight to implementation — caught, flagged transparently, and backfilled
before continuing, rather than left as a silent gap. The same happened with `docs/PRD.md` and
`docs/LLD.md` later in the project. Both are disclosed here rather than omitted from this case
study.

**Trade-off accepted, not hidden**: no rate limiting, no scheduled cleanup of the revocation
table, and no `SECRET_KEY` rotation exist — reasonable for a project at this scope, explicitly
documented as gaps rather than silently absent (`docs/SECURITY.md` §10).

## Results

101/101 automated tests passing (80 backend, 21 frontend), 0 lint errors,
clean TypeScript build. Live-verified: `docker compose up --build` produces two healthy
containers with automatic database migrations, and a scripted 14-point end-to-end check
(registration through logout-then-revocation-confirmed) passed against that real running
stack, not just the unit-test SQLite double. Load testing has not been performed — stated
explicitly rather than estimated.
